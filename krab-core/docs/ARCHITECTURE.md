# krab: архитектура

> **Если ты читаешь это в 3 часа ночи и не помнишь, что это:** krab это локальное зашифрованное хранилище секретов (пароли, ключи, заметки, TOTP-коды) на Rust. Всё лежит в одном зашифрованном файле. Без мастер-пароля файл выглядит как случайный мусор. Проект открытый. Сначала пишем ядро-библиотеку и консольную программу, интерфейс потом.
>
> **Статус:** код не написан, Rust в окружении ещё не ставили. Этот документ фиксирует все решения, принятые до начала кода. Старые `ARCHITECTURE.md` и `BUILD-PLAN.md` (про Flutter и SQLCipher) **устарели и больше не действуют**.

| Что | Имя |
|---|---|

| Будущая консольная программа | `krab-cli` (пока не создана) |
| Расширение файла хранилища | `.krabic` (только подсказка для человека и системы; файл узнаётся по `KRAB` в начале, а не по имени) |

Раньше рассматривали семейство «Nyx» (Nyx Diary, NyxD и т.д.) и кучу вариантов для ядра (Nyxide, Sideros, Carapace и др.). Всё это **отброшено**, имя выбрано. Открыто только одно: остаётся ли «Nyx + слово» брендом для пользовательского приложения, или бренд просто `krab`. Это ничему не мешает, решим позже.

## 2. Модель угроз

**Защищаем от:**
- потери или кражи устройства;
- холодного доступа к файлу (кто-то скопировал файл хранилища и пытается его вскрыть, в том числе перебирая пароль).

**НЕ защищаем от:**
- вредоносного ПО на работающей системе;
- дампа памяти работающей системы.

В CLI ключ живёт в памяти секунды: открыл, сделал дело, забыл. Занулять секреты в памяти (`zeroize`) всё равно надо, но это гигиена, а не гарантия.

**Главное правило, которое нельзя забывать:** формат файла, его «непонятность» и бинарность **не** являются защитой. Защита это только шифр и пароль. Не надеемся на «сложно прочитать».

## 3. Структура проекта

```
krab/                  <- workspace (папка, в которой несколько крейтов)
├── Cargo.toml         <- описание workspace
├── ARCHITECTURE.md    <- этот файл
└── krab-core/         <- библиотека: формат файла, крипто, модель данных, логика
```

Принцип: **`krab-core` хранит и считает, интерфейс показывает.** Вся логика (шифрование, формат, валидация, поиск, теги) живёт в ядре. CLI и любой будущий интерфейс только вызывают ядро. Как красиво показать теги, чем раскрасить, как сгруппировать, решает интерфейс и не трогает ни формат, ни ядро.

## 4. Формат файла хранилища

Файл состоит из открытого заголовка и зашифрованного тела.

```
[ заголовок 54 байта, открытый ] [ тело: зашифровано ] [ пломба 16 байт ]
```

### 4.1. Заголовок (54 байта, числа little-endian)

| Смещение | Размер | Поле | Что это |
|---|---|---|---|
| 0 | 4 | magic | байты `KRAB` (`4B 52 41 42`) |
| 4 | 1 | версия | версия формата, сейчас `1` |
| 5 | 4 | память | параметр Argon2id, **в KiB** (число идёт в Argon2 как есть, без пересчёта) |
| 9 | 4 | проходы | параметр Argon2id |
| 13 | 1 | параллелизм | параметр Argon2id |
| 14 | 16 | соль | случайная, для KDF |
| 30 | 24 | nonce | случайный, для шифра, **новый при каждом сохранении** |

Итого 54 байта. Дальше идёт зашифрованное тело, на конце которого 16 байт пломбы (auth tag).

### 4.2. Почему заголовок простой и фиксированный

Заголовок читается **до** проверки пломбы, то есть мы разбираем байты, которым ещё нельзя доверять. Поэтому парсер максимально тупой: читаем N байт по известным смещениям, и всё. Никакого CBOR или другого сложного формата для заголовка. Сложность допустима только в теле, потому что к моменту его чтения пломба уже подтвердила, что данные целые.

Новое поле в заголовке = новая версия формата. Для этого версия и существует.

### 4.3. Что открыто, а что нет, и почему

Заголовок не шифруется, потому что соль и параметры KDF нужны **для получения ключа**: иначе замкнутый круг (чтобы прочитать данные для получения ключа, нужен ключ). Эти данные не секретны, сами по себе они ничего не дают без пароля.

Но подменить заголовок нельзя: **весь заголовок (все 54 байта) подаётся в шифр как AAD**, то есть входит в расчёт пломбы. Изменил хоть байт (например, подсунул слабые параметры KDF) и пломба не сойдётся.

### 4.4. Тело

Тело это **весь список записей, сериализованный в CBOR и зашифрованный одним блоком**. Не по записям, а целиком.

## 5. Криптография

| Задача | Выбор | Крейт (ориентир) |
|---|---|---|
| Шифр + пломба | XChaCha20-Poly1305 (AEAD), nonce 24 байта | `chacha20poly1305` |
| Пароль → ключ | Argon2id | `argon2` |
| Сериализация тела | CBOR | `ciborium` |
| Затирание секретов в памяти | zeroize | `zeroize` |
| Случайные числа | из операционной системы | `getrandom` / `rand` |

### 5.1. Как это работает по шагам

**Сохранение:**
1. Берём 24 свежих случайных байта из ОС: новый **nonce**. (Соль остаётся той же, что у хранилища.)
2. Собираем заголовок (с новым nonce).
3. Сериализуем записи в CBOR.
4. Шифруем: ключ + nonce + AAD (весь заголовок) → шифротекст + пломба.
5. Пишем файл **безопасно**, см. раздел 6.

**Открытие:**
1. Читаем заголовок, проверяем `KRAB` и версию.
2. **Проверяем параметры Argon2id на допустимые границы** (раздел 5.3). Если за границами, сразу отказ.
3. Спрашиваем пароль. Argon2id: пароль + соль + параметры → ключ.
4. Расшифровываем: ключ + nonce из файла + AAD. Если пломба не сошлась, ошибка «неверный пароль или файл повреждён» (эти два случая различить нельзя, и это нормально).
5. Разбираем CBOR, работаем с данными в памяти.
6. Ключ и открытые данные зануляем, когда они больше не нужны.

### 5.2. Правила, которые нельзя нарушать

1. **Nonce никогда не повторяется с одним ключом.** Новый случайный nonce при **каждом** сохранении, без исключений. Повтор позволяет атакующему сложить два шифротекста, сократить гамму и получить XOR двух открытых текстов, а потом угадыванием вытащить данные и даже подделать пломбу.
2. **Заголовку не доверять**, пока пломба не проверена. Границы параметров проверять до выделения памяти.
3. **Не придумывать свою криптографию.** Только проверенные крейты и стандартные схемы.
4. Секреты в памяти зануляем (`zeroize`).

### 5.3. Параметры Argon2id: адаптивные

- При **создании** хранилища программа замеряет скорость машины и подбирает параметры под целевую паузу порядка 0,5–1 секунды. Результат пишется в заголовок.
- При **открытии** параметры берутся из заголовка, ничего заново не подбирается. Иначе ключ не получится.
- **Потолок при подборе** (память не выше разумного максимума, ориентир 256 MiB), чтобы файл гарантированно открывался на обычном ноутбуке. Сценарий: сломался комп, открываю с ноута.
- **Границы допустимого зашиты в код** (минимум и максимум каждого параметра). Хардкодим только границы, не сами значения:

  | Параметр | Допустимо при открытии | Подбор при создании |
  |---|---|---|
  | память | 19456 … 1048576 KiB (19 MiB … 1 GiB) | до 262144 KiB (256 MiB) |
  | проходы | 1 … 10 | под паузу 0,5-1 с |
  | параллелизм | 1 … 8 | под машину |

  Нижняя планка памяти (19 MiB) это минимум по рекомендациям OWASP, ниже которого файл не принимается. Верхние границы с запасом над потолком подбора, чтобы потолок можно было поднять позже, и старые и новые файлы продолжали открываться. **Расширять** границы безопасно, **сужать** осторожно: файлы, созданные раньше, могут перестать проходить проверку.
- Нужна команда «перенастроить KDF» (пересоздать ключ с параметрами текущей машины), в том числе при смене пароля.

### 5.4. Что было отвергнуто и почему

- **Шифровать по записям.** Утекает число и размеры записей, нужна отдельная защита от удаления и перестановки записей. Для килобайтов данных выгоды нет, расшифровка целиком занимает миллисекунды.
- **JSON для тела.** Нет типа «байты», возня с base64 для секретов, числами и датами.
- **postcard/bincode.** Не самоописываемые, любое изменение структуры ломает совместимость.
- **AES-256-GCM.** Нормальный, но nonce 12 байт, и риск повтора выше. Для открытого проекта без требований FIPS длинный случайный nonce убирает целый класс ошибок. FIPS нам не нужен.
- **scrypt, PBKDF2.** Argon2id современнее, PBKDF2 не требует памяти и быстро перебирается на видеокартах.
- **CBOR в заголовке.** Сложный парсер на недоверенных данных, плюс проблемы с AAD (нужны именно те байты, что в файле).
- **Непрозрачный magic.** Безопасность через неясность, формат всё равно выдаётся длиной и структурой.

## 6. Запись на диск (защита от обрыва)

Если питание пропадёт посреди записи, хранилище не должно потеряться. Поэтому:

1. Пишем новую версию во **временный файл** рядом с основным.
2. Убеждаемся, что запись полностью завершена (flush/fsync).
3. **Атомарно переименовываем** временный файл поверх основного.

В любой момент на диске лежит либо целиком старый, либо целиком новый файл.

## 7. Модель данных (черновик)

Хранится внутри зашифрованного тела (CBOR).

**Запись (Entry):**
- `id`: UUID
- `type`: тип записи, один из `login` | `note` | `key` | `totp` | `other` (набор фиксирован в ядре, ядро делает базовую валидацию и даёт шаблоны полей)
- `title`: название
- `note`: заметка
- `favorite`: избранное
- даты: создания и изменения
- `source`: необязательная строка, свободный текст: к какому сервису или чему принадлежит запись, или откуда пришёл пароль (например, `github.com`, `Сбербанк`, `рабочий VPN`). Не путать: `title` это как запись называется, `source` это к чему она относится, `url` внутри полей это конкретная ссылка для входа. Поиск смотрит и в `source`
- `fields`: список полей
- `tags`: список тегов

**Поле (Field):**
- `label`: метка
- `value`: значение
- `kind`: `text` | `secret` | `url` | `multiline` | `totp`

**Теги:** просто строки внутри записи. Нормализация (обрезка пробелов, регистр) делается в коде ядра. Справочника тегов нет. Поиск самый базовый. Фильтры по тегам (И / ИЛИ), сортировки и раскладка тегов в интерфейсе это логика программы и интерфейса, формат файла не затрагивают.

**Типы записи:** если ядро встречает тип, которого не знает (файл создан более новой версией), оно читает его как `other`, но при сохранении записывает обратно **как был**, чтобы ничего не потерять.

**Удаление:** корзины нет. Удаление окончательное, интерфейс обязан просить подтверждение. Что это значит на самом деле: в новой версии файла записи уже нет (файл пишется целиком из памяти без неё), в памяти программы её данные затираются (`zeroize`). Чего **не** гарантируем: физического стирания байтов на диске (особенно SSD) и чистоты старых копий и бэкапов файла. Они остаются зашифрованными, и от холодного доступа защищает шифр, а не стирание. Формулировка везде честная: «удалено из хранилища», а не «стёрто с диска». Откат заменяют подтверждение и бэкапы файла.

### Решения по модели

| Вопрос | Решение | Почему |
|---|---|---|
| История секретных полей | **Нет** | Каждое лишнее хранимое значение это ещё один секрет, который утечёт вместе с файлом. Добавить позже можно без смены версии формата (CBOR совместим) |
| Папки или теги | **Только теги** | Проще, гибче (запись в нескольких категориях), иерархию можно имитировать именем `банк/сбер` |
| Теги: строки или справочник | **Строки** | Справочник это лишнее на старте, добавить позже можно необязательным полем |
| Тип записи | **Фиксированный набор в ядре** | Даёт шаблоны, иконки и базовую валидацию. Свободная строка это второй набор тегов с опечатками, а полное отсутствие типа усложняет интерфейс |
| Поле `source` | **Необязательная строка: к чему относится / откуда** | Полезно для поиска и группировки по сервису, ничего не стоит |
| Корзина | **Нет, удаление окончательное** | Удалённые секреты не должны лежать в файле. Откат заменяют подтверждение и бэкапы |

## 8. Решения одним списком

1. Тело шифруется **целиком одним блоком**.
2. Сериализация тела: **CBOR**.
3. Шифр: **XChaCha20-Poly1305**, nonce 24 байта, новый при каждом сохранении.
4. KDF: **Argon2id**, параметры подбираются при создании хранилища и пишутся в заголовок.
5. Заголовок: **фиксированная двоичная раскладка**, little-endian, 54 байта, весь идёт как AAD.
6. Magic: **`KRAB`**.
7. Запись: через временный файл + атомарное переименование.
8. История секретных полей: **нет**.
9. Организация: **только теги**, строками.
10. Память Argon2id в заголовке: **в KiB**, без пересчёта.
11. Границы Argon2id: память 19 MiB … 1 GiB, проходы 1 … 10, параллелизм 1 … 8, потолок подбора 256 MiB.
12. Тип записи: **фиксированный набор** (`login`, `note`, `key`, `totp`, `other`), неизвестный тип читается как `other` и сохраняется как был.
13. `source`: необязательная строка «к чему относится / откуда».
14. Корзины нет, удаление **окончательное** с подтверждением.
15. Расширение файла: **`.krabic`**.

## 9. Словарь (для 3 часов ночи)

- **Крейт (crate):** пакет Rust. `krab-core` это крейт-библиотека.
- **Workspace:** папка с несколькими крейтами под одним `Cargo.toml`.
- **Cargo:** сборщик и менеджер пакетов Rust. Файлы кода имеют расширение `.rs`.
- **KDF:** намеренно медленная функция «пароль + соль → ключ». Медленная, чтобы перебор паролей был дорогим.
- **Соль (salt):** случайные данные, которые подмешиваются к паролю в KDF. Лежат в файле открыто. Нужны, чтобы один и тот же пароль не давал один и тот же ключ у всех.
- **Nonce:** «число, используемое один раз». Случайное число, которое вместе с ключом определяет гамму шифра. Лежит в файле открыто, секретным быть не должно. Его задача **не повторяться**, чтобы каждое шифрование одним и тем же ключом давало разный результат.
- **Гамма:** поток псевдослучайных байтов, который накладывается на данные операцией XOR. `гамма = функция(ключ, nonce)`. Знаешь nonce, но не знаешь ключ: гамму не получить.
- **XOR:** побитовое «исключающее ИЛИ». Обратим: `(A XOR B) XOR B = A`. Поэтому два шифротекста с одной гаммой при сложении сокращают гамму.
- **AEAD:** шифр, который одновременно шифрует и даёт пломбу.
- **Пломба (auth tag):** контрольная метка, считается с участием секретного ключа. Показывает, что данные не изменяли и что расшифровка идёт верным ключом. Не сошлась: «неверный пароль или файл повреждён».
- **AAD:** дополнительные данные (у нас заголовок). Не шифруются, но входят в пломбу, поэтому подмена ломает расшифровку.
- **CBOR:** двоичный «JSON» (RFC 8949): есть тип «байты», самоописываемый, поля можно добавлять без поломки старых файлов.
- **FIPS:** американские стандарты по криптографии для госструктур и корпораций. Нам не нужны.
- **zeroize:** затирание секретов в памяти нулями после использования.
